MAIL SENTINEL

Intelligent Email Phishing Detection & Threat Analysis Platform

Build a complete, production-quality cybersecurity web application called Mail Sentinel.

Tagline

Detect the Threat. Protect the Inbox.

Mail Sentinel is an intelligent email phishing detection and threat-analysis platform. Users can paste an email or upload an ".eml" file, analyze it, and receive an explainable phishing-risk assessment.

The project must prioritize:

- Security
- Explainability
- Detection accuracy
- Clean architecture
- Maintainable code
- Responsive UI
- Local ML inference
- Clear error handling

Do not add unrelated features.

2. CORE ML APPROACH

The primary text-classification model must be:

TF-IDF + Logistic Regression

Use this as the baseline phishing classifier.

The system may also use:

XGBoost

for structured email and URL features.

Do not use an LLM as the primary phishing classifier.

The core application must work without any paid AI API.

6. SENDER ANALYSIS

Analyze:

- Sender email syntax
- Sender domain
- Reply-To mismatch
- Display-name spoofing
- Domain similarity
- Suspicious characters
- Brand impersonation indicators
- Free-mail domain usage where relevant

Do not classify an email as malicious solely because it uses Gmail, Yahoo, Outlook, or another free-mail provider.

---

7. URL ANALYSIS

Extract URLs from both plain-text and HTML email content.

Analyze:

- URL length
- Domain length
- Number of subdomains
- URL encoding
- Suspicious characters
- IP-address URLs
- Redirect indicators where safely testable
- Suspicious TLDs
- HTTPS presence
- Domain mismatch
- Brand impersonation
- Login/verification/payment-related paths
- Punycode/IDN indicators
- Suspicious query parameters

Do not automatically visit arbitrary URLs.

URL analysis must be passive by default.

Display every extracted URL in the results.

---

8. NLP / CONTENT ANALYSIS

Analyze subject and body content.

Detect indicators such as:

- Urgency
- Fear/threat language
- Credential requests
- Password-reset requests
- Payment requests
- Account suspension claims
- Prize/reward scams
- Social engineering
- Suspicious calls to action
- Brand impersonation language

Use TF-IDF for ML classification.

Do not rely exclusively on keyword matching.

Rule-based detection should be an additional signal.

---

9. HEADER ANALYSIS

Analyze available headers for:

- Received-chain anomalies
- Return-Path mismatch
- Reply-To mismatch
- Authentication-Results
- Originating-domain inconsistencies
- Suspicious routing information
- Missing or unusual headers

Never fabricate unavailable header information.

If information is unavailable, display:

Not Available

---

10. SPF / DKIM / DMARC

If authentication results are present in the email headers, extract and display:

- SPF
- DKIM
- DMARC

Possible states:

PASS
FAIL
SOFTFAIL
NEUTRAL
NONE
UNKNOWN

Clearly distinguish between authentication results found in the email headers and independently verified results.

Do not perform active checks unless explicitly implemented as a separate safe feature.

---

11. ATTACHMENT ANALYSIS

List attachments without executing them.

Extract:

- Filename
- Extension
- MIME type
- Size
- Suspicious extension indicators
- Double-extension patterns

Examples:

invoice.pdf.exe
document.docm
payment.zip

Do not execute or open potentially malicious files.

Do not claim an attachment is malware merely because of its extension.

12. MACHINE LEARNING

Create a complete training pipeline:

Dataset
    ↓
Cleaning
    ↓
Text Preprocessing
    ↓
Train/Test Split
    ↓
TF-IDF
    ↓
Logistic Regression
    ↓
Evaluation
    ↓
Save Model

Save trained artifacts using Joblib.

Required metrics:

- Accuracy
- Precision
- Recall
- F1-score
- Confusion matrix

Use stratified splitting where appropriate.

Avoid data leakage.

Store training code separately from inference code.

The backend must load the trained model instead of retraining it for every request.

---

13. RISK ENGINE

Create a dedicated risk-scoring service.

Combine:

- ML prediction
- Sender analysis
- URL analysis
- Content analysis
- Header analysis
- Authentication analysis
- Attachment analysis

Risk levels:

0–29    LOW
30–59   MEDIUM
60–79   HIGH
80–100  CRITICAL

The scoring system must be deterministic and documented.

Do not let the ML model alone determine the final score.

Example:

{
  "score": 87,
  "severity": "CRITICAL",
  "confidence": 0.93
}

---

14. EXPLAINABLE RESULTS

Every detection must include evidence and reasons.

Example:

CRITICAL RISK — 87/100

Reasons:
- Sender domain does not match the claimed organization
- Suspicious credential-verification URL detected
- Authentication failure detected
- Urgency-based social engineering language detected
- ML model classified the email as phishing with high confidence

Do not generate explanations that contradict the actual analysis results.

37. IMPORTANT IMPLEMENTATION RULES

- Write real working code.
- Do not create fake ML predictions.
- Do not hardcode phishing results.
- Do not create fake threat-intelligence responses.
- Do not fabricate unavailable information.
- Keep frontend and backend responsibilities separate.
- Use TypeScript types for API responses.
- Use Pydantic schemas for backend validation.
- Keep services modular.
- Avoid unnecessary dependencies.
- Avoid unnecessary abstractions.
- Keep the application easy to run locally.
- Do not add Docker.
- Do not use gradients.
- Do not add excessive animations.
- Do not sacrifice usability for visual effects.
- Do not expose secrets.
- Handle failures gracefully.

If an external threat-intelligence API is unavailable, Mail Sentinel must continue functioning using its local detection engine.

The project is complete only when a user can:

1. Start the backend.
2. Start the frontend.
3. Open Mail Sentinel.
4. Paste an email OR upload an ".eml" file.
5. Submit it for analysis.
6. Receive a phishing risk score.
7. See ML confidence.
8. See sender analysis.
9. See URL analysis.
10. See content analysis.
11. See authentication information when available.
12. See attachment analysis.
13. See clear reasons behind the score.
14. View previous scans.
15. View security statistics.
16. Run the application without any paid AI API.
17. Run automated tests successfully.

The final application should feel like a professional cybersecurity email-analysis platform, with a clean SOC-style interface and an explainable detection engine.

Build incrementally. Verify each major module before proceeding to the next module. Resolve implementation errors before continuing.
